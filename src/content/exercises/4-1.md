question: "Imagine you're building a bookmark API where you have bookmarks for specific URLs online and can arrange these in different folders. Do you model this as two separate resources (Bookmark and Folder) or a single resource (e.g., Entity), with a type in-line to say whether it's acting as a folder or a bookmark?"
date: 2022-09-28
---

> 💡 Fun fact: This exercise is one of the ones we used to debate in Google's API Design Class. It's fascinating how many unique answers there are for the resource layout of something so seemingly simple!

First, let's look at the two options being proposed. First, we have two separate resources (`Bookmark` and `Folder`), each with their own identifier.

```typescript
interface Bookmark {
  id: string;
  url: string;
  folderId?: string;
}

interface Folder {
  id: string;
  displayName: string;
  folderId?: string;
}
```

*Option 1: Two separate resources (Bookmark and Folder)*

The other is a more generic design, using polymorphism (see Chapter 16: Polymorphism) with a single resource (`Entity`).

```typescript
interface Entity {
  id: string;
  type: "folder" | "bookmark";
  folderId?: string;
  details: BookmarkDetails | FolderDetails;
}

interface BookmarkDetails {
  url: string;
}

interface FolderDetails {
  displayName: string;
}
```

*Option 2: A single polymorphic resource (Entity)*

Option 1 uses a standard referential relationship, where each `Bookmark` resource belongs to a single `Folder` resource. Option 2 uses a single `Entity` resource with a self reference that points to another `Entity` resource. This works out quite well because both "types" can live inside folders (i.e., this supports nested folders).

##### So why choose one over the other?

One big benefit of using a single `Entity` resource (even if the name needs some work) is that you can list all of the data with a single API call like `ListEntities()`. You can take the output of this API call and build your bookmarks menu. This seems to align quite well with the stated goal of a bookmarks API.

On the other hand, if we have two distinct resource types, this means that since a folder can contain both bookmarks and other folders, in order to build a menu we'll have to make two separate API calls (`ListBookmarks()` and `ListFolders()`), often making one after another for each folder that we run into (`ListBookmarks(filter="folder:1234")`), which means quite a bit more traffic on the wire.

While this question seems to be more about the polymorphic aspect of the resource layout rather than the relational aspect, it's important to note that both options are perfectly valid (using either a standard reference relationship or a self-reference relationship). In the use case at hand though it seems that the polymorphic resource (`Entity`) is the better candidate.
