question: "In your company, storage systems use gigabytes as the unit of measurement (10<sup>9</sup> bytes). For example, when creating a shared folder, you can set the size to 10 gigabytes by setting `sizeGB = 10`. A new API is launching where networking throughput is measured in Gibibits (2<sup>30</sup> bits) and wants to set bandwidth limits in terms of Gibibits (e.g., `bandwidthLimitGib = 1`). Is this too subtle a difference and potentially confusing for users? Why or why not?"
date: 2022-09-25
---

This is a tricky question, but ultimately comes down to consequences. Let's assume that users will make mistakes with these fields and assume `Gib` and `Gb` are the same. What will happen when they make this mistake? Will it be catastrophic? Or is it more of an inconvenience?

To better understand this, let's look at how many "bytes" are involved here:

| Unit | Abbreviation | Amount (bytes) |
| --- | --- | --- |
| Gibibit | `Gib` | `134,217,728 bytes` |
| Gigabyte | `GB` | `1,000,000,000 bytes` |
| Difference |  | `865,782,272 bytes` (~865 Megabytes) |

As you can see here, there is quite a big difference per unit: 1 Gibibit is only ~135 Megabytes, whereas 1 Gigabyte is 1,000 Megabytes, about a 7x difference for the two units. If we were using these both for storage values (e.g., `sizeGB` as well as `sizeGib`), this would be a huge problem. Can you imagine asking thinking you're asking for 500 GB and actually getting ~70 GB? Or asking for 500 GB and getting 3.5 TB? That might be a bit more than an inconvenience - it could be a costly mistake.

The subtlety of the problem arises when we realize that we're using one unit as the standard for network bandwidth and the other as the standard for storage space. But is this really a problem? Should we prohibit similar units to different concepts simply because they're similar? Or because they're measuring the same base unit (in this case, bits) in different group units?

Taking this to an absurd degree, it's a bit like asking whether we should avoid using `ageYears` because we use `appointmentDurationMinutes` elsewhere in the API . The units apply to entirely different concepts, domains, and scenarios, so it seems unreasonable in this absurd example to not use the right unit for the job, despite both measuring a base unit (in this case time, so... seconds?). Yes, the naming is more subtle (just a single letter difference), but assuming these are the industry standards for measuring these values (Gibibits for network bandwidth, Gigabytes for storage space), this should be the basic assumption by users.

In fact, it might be more confusing, for example, to measure network bandwidth in Gigabytes and lead to users allocating ~7x more bandwidth than they intended by setting `networkBandwidthLimitGB=10` expecting a 10 Gibibit limit but actually getting a ~70 Gibibit limit because they actually set a 10 Gigabyte limit.

In short, this is a tough one, but if I had to choose, I'd say it's fine to have these two fields using these two units. This is based on the fact that the values are fundamentally different (storage space versus network bandwidth) and each value uses the industry standard unit.
